# Nidio

Приложение для пар: совместные задачи и календарь.

## Локальный запуск

Нужны Node.js 24, pnpm 11.15.1 и запущенный Docker Desktop. Все команды выполняются из корня проекта.

```bash
pnpm install --frozen-lockfile
pnpm db:up
```

Создайте `apps/api/.env.development`:

```env
NODE_ENV=development
PORT=4000
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/nidio
DIRECT_URL=postgresql://postgres:postgres@localhost:5432/nidio
JWT_SECRET=local-development-secret-change-before-production
FRONTEND_URL=http://localhost:3000
API_PUBLIC_URL=http://localhost:4000
STORAGE_PROVIDER=minio
STORAGE_ENDPOINT=http://localhost:9000
STORAGE_REGION=us-east-1
STORAGE_ACCESS_KEY=minio
STORAGE_SECRET_KEY=minioadmin
STORAGE_BUCKET=nidio
```

Для отправки писем дополнительно задайте `GMAIL_USER` и `GMAIL_APP_PASSWORD` (пароль приложения Gmail). Без них отправка писем не работает, при старте API будет сообщение об ошибке SMTP.

Создайте `apps/web/.env.development.local`:

```env
NEXT_PUBLIC_API_URL=http://localhost:4000
NEXT_PUBLIC_GRAPHQL_URL=http://localhost:4000/graphql
NEXT_PUBLIC_REALTIME_URL=http://localhost:4000
```

Если уже есть `apps/web/.env.local`, проверьте, что в нём нет конфликтующих адресов API.

После запуска PostgreSQL и MinIO подготовьте базу и запустите приложение:

```bash
pnpm --filter api db:deploy
pnpm --filter api db:seed:templates
pnpm dev
```

Приложение: http://localhost:3000. API: http://localhost:4000. Консоль MinIO: http://localhost:9001 (`minio` / `minioadmin`).

Для остановки приложения нажмите `Ctrl+C`, для остановки PostgreSQL и MinIO выполните `pnpm db:down`.

## Проверка API и мониторинг Render

Публичный `GET /health` (также `HEAD /health`) отвечает `200` и `{"status":"ok"}` без авторизации. Ответ не кешируется. Это проверка доступности процесса API, без запросов к базе и внешним сервисам.

После деплоя настройте внешний HTTP-монитор:

- URL: `https://<имя-api-сервиса>.onrender.com/health` — именно API, не сайт на Vercel.
- Метод: `GET`, интервал: 5 минут, ожидаемый статус: `200`.
- Для проверки уже заснувшего сервиса учитывайте холодный старт около минуты.
- В Render → Settings → Health Checks укажите `/health` для проверки состояния при деплое. Это отдельная настройка, не замена внешнему мониторингу.

Free-сервис засыпает после 15 минут без входящего трафика. Регулярные внешние запросы поддерживают активность, но не отменяют перезапуски и ограничения тарифа: 750 часов в месяц на workspace, суммарно для всех бесплатных сервисов. См. [Render Free](https://render.com/docs/free) и [Health Checks](https://render.com/docs/health-checks). Мониторинг и настройки Render не включаются автоматически этим изменением кода.

Удаление чата: новая миграция `20261017000000_remove_chat` удаляет историю сообщений и связанные таблицы. Сохраните резервную копию нужных данных перед её применением. Исторические миграции сохранены; миграция не запускается автоматически при разработке, но применяется командой `db:deploy` (в том числе при `start:render`).

### Сессия установленной PWA

Запросы `/auth/*` идут через Next.js rewrite на `NEXT_PUBLIC_API_URL`. Браузер
получает HttpOnly refresh-cookie на домене веб-приложения, а не стороннего API.
Путь `/auth/refresh` сохраняется без префикса, чтобы соответствовать пути cookie.
`NEXT_PUBLIC_API_URL` должен содержать адрес API, не адрес самого frontend.
После изменения этой настройки требуется пересборка frontend. После перехода со
старой версии пользователю потребуется один вход для получения новой cookie.

Проверка после деплоя: войти в установленную PWA на iPhone, закрыть её полностью,
открыть снова и проверить восстановление сессии. При недоступном сервере должен
появляться повтор подключения, а не принудительный переход на вход. Проверить
также явный выход: последующее открытие должно запросить авторизацию.

### Готовность базы и метрики

- `/health` остаётся проверкой процесса без базы.
- `/health/ready` проверяет соединение с PostgreSQL и доступность `CoupleMember.savingsColor`: `200` при успехе, `503` при ошибке или ожидании более 2 секунд. Одновременные проверки объединяются. Это не полная проверка всех миграций: её выполняют тесты и `prisma migrate deploy`.
- `HTTP_METRICS=1` на API включает структурированные записи `http_request` со временем, статусом и шаблоном маршрута. Без переменной пишутся только ответы 5xx и запросы дольше секунды. Токены, параметры URL и тела запросов не записываются. Из этих записей можно считать p50/p95 и долю 5xx в используемом сборщике логов.
- `NEXT_PUBLIC_PERFORMANCE_METRICS=1` на web **до сборки** включает отправку LCP, INP, CLS, FCP и TTFB в `/api/metrics` для случайных 10% загрузок страницы. Записи `web_vital` появляются в логах web-хостинга. Идентификаторы пользователей и URL с параметрами не передаются. Endpoint ограничивает размер тела и количество записей на экземпляр. Это диагностическая выборка, не биллинг и не точный счётчик посетителей.
- Внешний монитор для `/health/ready`, графики и уведомления нужно настроить в вашем хостинге/сборщике логов. Код сам не создаёт внешние сервисы мониторинга.

### Обновление API финансов

Новый web использует `/finance/sections/:section`, `/finance/goal/:id`, `/finance/budget`, `/finance/budget-limits`, а также `/finance/goal/:id/history` и `/finance/goal/:id/contribution`. Истории возвращаются страницами по 50 записей с `nextCursor`. Суммы считаются на сервере по всем подходящим операциям, независимо от страницы. CSV выгружает все страницы выбранного фильтра.

Сначала разверните API, затем web. Старый `/finance` сохранён для уже открытых/закешированных версий приложения. Новая версия его не вызывает. Миграция БД для этих изменений не требуется.

При подключённом WebSocket периодический опрос финансов отключён. Изменения, переподключение и возврат к устаревшим данным запускают сверку; при отключённом WebSocket действует резервный опрос раз в 30 секунд. Ошибка фонового обновления сохраняет видимые данные с предупреждением, но ответы 401/403 скрывают их.
